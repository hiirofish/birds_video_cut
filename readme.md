# 🐦 鳥の巣ライブカメラ用・動き検出＆動画クリッピングシステム

定点観測された鳥の巣の長時間動画（8〜16時間/日）から、鳥などの動きがあった部分のみを検出し、OP/ED付きのハイライト動画として自動生成するシステムです。

コシアカツバメの巣の24時間ライブカメラ映像を毎日処理するために開発しました。同じような「定点カメラの長時間動画から動きだけ抽出したい」ユースケースに使えます。

## スクリプト構成

| スクリプト | 用途 | 特徴 |
|---|---|---|
| `smart_bird_pipeline.py` | **全自動パイプライン（推奨）** | YouTube APIで配信終了を検知 → DL → 動体検知 → 結合 → チャットログ統合まで全自動。DL失敗時は手を変えて自動リトライし、完遂を優先（v6.0で大幅強化） |
| `fast_bird_pipeline.py` | 本番用（手動DL済みの場合） | tbn正規化 → 検知 → 切り出し → OP/ED付き結合を1コマンドで実行。再エンコードなし（`-c copy`）で高速 |
| `motion_detector.py` | 旧版（切り出しのみ） | コマンドライン引数で細かく調整可能。結合は別途手動で行う |
| `cut_clips.py` / `compile_shorts.py` | コメントベースのショート生成（**POC**） | チャットログの時報コメントから見どころを切り抜き、字幕焼き込み→スワイプ転換で結合。詳細は下記「🎬 コメントベースのショート自動生成」参照 |
| `upload_videos.py` | YouTubeへの公開アップロード | まるごと版とショート版を公開し、それぞれの再生リストへ振り分け。二重投稿防止つき。詳細は下記「📤 YouTubeへの自動アップロード」参照 |

> **⚠️ 入力フォルダの違いに注意**
> - `smart_bird_pipeline.py`: 入力フォルダの作成・動画DLを自動で行う → `python smart_bird_pipeline.py`
> - `fast_bird_pipeline.py`: `input/0610/` 配下に動画を配置 → `python fast_bird_pipeline.py 0610`
> - `motion_detector.py`: `input/` 直下に動画を配置 → `python motion_detector.py`（従来通り）

## 📦 セットアップ

### 必要なもの

- Python 3.x
- OpenCV, NumPy, requests ライブラリ
- FFmpeg（パスが通っていること）
- yt-dlp（`smart_bird_pipeline.py` を使う場合）
- YouTube Data API v3 のAPIキー（`smart_bird_pipeline.py` を使う場合）
- Linux環境のフォント（`/usr/share/fonts/opentype/noto/NotoSansCJK-Bold.ttc`）※ OP焼き込み用

```bash
pip install opencv-python numpy requests
```

```
AIzaSy_YOUR_API_KEY_HERE
```

```bash
pip install yt-dlp
```

2. 検索バーで「YouTube Data API v3」を検索し、有効化
3. 「認証情報」→「＋認証情報を作成」→「APIキー」でキーを発行
4. **【重要】** キーの設定画面で「APIの制限」→「YouTube Data API v3」のみにチェックを入れて保存

> 💡 今回の用途は「配信ステータスの監視」（公開情報の読み取り）だけなので、OAuth 2.0 ではなくAPIキーで十分です。

## 🤖 smart_bird_pipeline.py（全自動・推奨）

「寝る前にコマンドを1回叩けば、朝起きたらダイジェスト動画ができている」を実現するスクリプトです。

YouTube APIで対象チャンネルのライブ配信を監視し、DL → 動体検知 → OP/ED付き結合までを全自動で実行します。

### 実行方法

```bash
python smart_bird_pipeline.py
```

これだけ。あとは寝るだけ。

### 処理の流れ

1. **未処理の日付を一括検出** — 過去7日以内（`LOOKBACK_DAYS`）で `marugoto/` に成果物がない日付を**すべて**洗い出し、古い順に処理。配信の一覧はチャンネルの「アップロード済み動画」プレイリストから取得します（`search.list` は取りこぼす → 罠5）
2. **配信終了を確認** — 全配信が終了（`liveBroadcastContent == "none"`）していない日付はスキップし、他の日付の処理を続行
3. **クライアント並列診断** — 5種類のプレイヤークライアントに**同時に**問い合わせ、実際に利用可能なフォーマット一覧を取得。使えるものだけを選ぶ
4. **ダウンロード** — 実在する具体的なフォーマットID（例 `136+140`）を指定してDL。配信開始時刻順に `0615-1.mp4`, `0615-2.mp4` と自動リネーム
5. **完成検証** — `ffprobe` でコーデック・尺を確認し、さらに `ffmpeg -sseof` で**末尾を実際にデコード**して尻切れを検出。不合格なら破棄して再取得
6. **動体検知→結合** — `fast_bird_pipeline.py` を自動キックし、ダイジェスト動画を生成
7. **チャットログ統合** — その日の全配信枠のコメントを実時刻順にマージし `marugoto/0615_output.txt` を生成
8. **完了** — 成功／スキップ／失敗を集計して表示

### 中断・再実行しても安全

途中で `Ctrl+C` しても、DL済みの動画は次回起動時に検証のうえスキップされます。未完了分は `--continue` により**続きから再開**するので、数GBを頭から落とし直すことはありません。

### 設定

スクリプト先頭の設定エリアで挙動を調整できます：

```python
CHANNEL_HANDLE = "@Take1bit"    # target channel
LOOKBACK_DAYS = 7               # how many days back to scan for unprocessed dates
DOWNLOAD_RATE_LIMIT = "5M"      # bandwidth cap; lower to "3M" if the link stalls
MAX_HEIGHT = 720                # resolution ceiling
DURATION_TOLERANCE = 0.02       # accept a download within 2% of the expected length
```

### ⚠️ YouTubeアーカイブの5つの罠

長時間ライブ配信のアーカイブを扱うには、独立した5つの落とし穴があります。罠1〜4はv6.0、罠5はv7.1で個別に対策しています。

#### 罠1: コーデックの混在（AV1/VP9）

YouTubeはアーカイブを裏で段階的に変換します。

- **配信終了直後** → H.264形式のみ提供
- **時間が経過すると** → AV1（高圧縮・高解像度）に変換される

同じ日の配信でも、朝の部はAV1/2160p、昼の部はH.264/1080p、とコーデックが異なることがあります。異なるコーデックが混在すると、FFmpegの `-c copy` 結合時にタイムスタンプが破壊されて動画が壊れます。

**対策**: 全段階でH.264（`avc1`）を強制。H.264が1つも見つからないクライアントは候補から除外します。

#### 罠2: 403 Forbidden（PO Token要求）

プレイヤークライアントによっては、取得したストリームURLがPO Token（Proof of Origin Token）を要求し、DL開始直後に `HTTP Error 403: Forbidden` で弾かれます。**同じ動画でもクライアントを変えれば通る**のが特徴です。

**対策**: DL前に5クライアントを並列診断し、実際に使えるものだけを選択。成功したクライアントは `logs/client_cache.json` に記録し、次回以降は診断をスキップします。

```python
CLIENT_VARIANTS = [
    [],  # yt-dlp's own default selection
    ["--extractor-args", "youtube:player_client=visionos,tv"],
    ["--extractor-args", "youtube:player_client=web_safari"],
    ["--extractor-args", "youtube:player_client=tv"],
    ["--extractor-args", "youtube:player_client=android_vr,web"],
]
```

#### 罠3: HLS（m3u8）の断片地獄

同じ動画でも、配送方式には **DASH**（1本の連続ファイル）と **HLS**（数秒ごとの断片）の2種類があります。8時間配信をHLSで落とすと**断片が5,000個以上**になり、接続オーバーヘッドで実効速度が1MB/s以下まで落ちます。

なおHLSとDASHは**配送方式の違いであってエンコードの違いではありません**（itag 136 はどちらもH.264 720p）。したがってDASHは「優先」するが「必須」にはしません。必須にすると、DASHを持たないクライアントに当たった瞬間に処理が止まってしまうためです。

**対策**: フォーマット選定を4段階のフォールバックにし、DASHを最優先しつつ、無い場合はHLSでも確実に落とします。

| 優先度 | 内容 |
|---|---|
| 1 | H.264 720p以下 / DASH |
| 2 | H.264 720p以下 / HLS可 |
| 3 | H.264（解像度不問） |
| 4 | 結合済みmp4 |

#### 罠4: 「完了したのに中身が無い」ファイル

DLを強制終了したタイミングによっては、**mp4のヘッダ（moovアトム）が本来の尺を主張したまま、実データが途中までしか無い**ファイルが生成されます。`ffprobe` の `duration` はヘッダを読むだけなので、この嘘を見抜けません。実際に、8時間と表示されるのに冒頭12分しか映っていないファイルが動体検知に流れ込む事故が発生しました。

**対策**: `ffmpeg -sseof` でファイルの**実際の終端付近を1フレームだけデコード**し、成功した場合のみ完成と判定します。

```python
# -sseof seeks relative to the REAL end of the stream, so a truncated file
# fails here even when its header still claims the full duration.
ffmpeg -v error -sseof -30 -i video.mp4 -frames:v 1 -f null -
```

#### 罠5: `search.list` は「あるはずの動画」を返さない

その日の配信を探すのに `search.list` を使っていましたが、この索引は**反映が遅れる上に取りこぼします**。2026-09-18 にはこのチャンネルで**9本しか返らず**、0914の朝枠が一覧から消えていました。

片方の枠しか見つからないと、その日はもう片方だけでダイジェストとチャットログが作られます。**出来上がりを見ても「朝は映っていない日」としか見えない**ので、欠けたこと自体に気づけないのが厄介なところです。

**対策**: チャンネルの「アップロード済み動画」プレイリスト（`channels.list` → `relatedPlaylists.uploads`）を `playlistItems.list` で全ページ列挙します。こちらは取りこぼしが無く、APIクォータも1ページ1単位（`search.list` は1回100単位）で済みます。`smart_bird_pipeline.py` と `extract_daily_chat.py` の両方を同じ方式にしてあります。

## 🎬 コメントベースのショート自動生成（POC）

> **⚠️ 実験中の機能です。** 動体検知だけに頼らず、視聴者コメント（時報コメント）を手がかりに
> 「見どころ」を切り抜き、コメントを字幕として焼き込んだショート動画を作るワークフローです。
> `smart_bird_pipeline.py` が生成する `marugoto/MMDD_output.txt`（チャットログ）を入力に使います。

### クイックスタート

新しいClaude Codeセッションで、こう頼めば①〜③を一気通貫でやってくれます。

```
0807のショート結合動画を作って
```

（`marugoto/MMDD_output.txt` がまだ無い＝その日の配信がまだ終わっていない場合は、そう教えてくれます）

### 全体の流れ（3ステップ、途中で人がレビューできる半自動）

```
marugoto/MMDD_output.txt          (チャットログ。既存の全自動パイプラインが生成)
        │  ① Claude Codeで /extract-clips MMDD を実行（文章の意味判断＝AI）
        ▼
marugoto/MMDD_clips.json          (クリップ候補。人がレビュー・修正できる)
        │  ② python cut_clips.py MMDD（決定的処理＝コード）
        ▼
marugoto/shorts/MMDD_<id>.mp4     (コメントごとの短尺クリップ、字幕焼き込み済み)
        │  ③ python compile_shorts.py MMDD（決定的処理＝コード）
        ▼
marugoto/MMDD_short_DAY<n>_<title>.mp4  (スワイプ転換でつないだショート。3分超なら_part1_/_part2_)
```

「意味の判断が要る部分（①）」と「機械的に正確さが要る部分（②③）」を分けているのがポイントです。
LLMに秒数計算をさせるとミスるので、LLMは「どのコメントを採用するか・余白はどれくらいか・
返信は同じ出来事の話か」だけを判断し、実際のファイル・オフセットへのマッピングと
ffmpeg実行はスクリプトに任せます。

### ① `/extract-clips MMDD` — クリップ候補の抽出

Claude Codeのスキル（`.claude/skills/extract-clips/SKILL.md`）としてルールを定義しています。
チャットログの各行を読み、以下を判断します。

| コメントの書き方 | 例 | 扱い |
|---|---|---|
| 秒単位の単発時刻 | `14:45:45 おちりのアップ` | 前後に余白（デフォルト前3秒/後8秒）を付けて採用 |
| 範囲指定 | `10:44:58～45:53 バッタさん持ち帰り` | その範囲＋前後2秒 |
| 分単位のみ | `9:36 入口に来てくれた` | 秒は`:00`と仮定し、後方に大きめの余白（`confidence: low`） |
| 並列した複数時刻 | `16:12:00と16:41からお口見えたよ!` | 1コメントから複数クリップを生成 |
| 挨拶・意味なし | `おはようございます` | スキップ |
| 配信者本人(`@Take1bit`)の発言 | `いつもコメントありがとうございます` | 内容によらずスキップ |
| 元コメントへの返信 | 「時報ありがとうございます、〜見えましたね」 | 元クリップの`replies`にマージ（**この判断はAIでないと出来ない**） |

出力は `marugoto/MMDD_clips.json`。`clips`（採用）と`skipped`（除外、理由付き）に分かれており、
`confidence: low` が付いたものは人が見直すとよいです。中身をエディタで直接編集してから
次のステップに進めます（間違ったクリップがあれば消す、余白を手で調整する、など）。

### ② `python cut_clips.py MMDD` — 切り出し＋字幕焼き込み

`marugoto/MMDD_clips.json` の壁時計時刻を実際のファイル・秒数に変換して `ffmpeg` で切り出し、
2行キャプション（1行目: `@author:`、2行目: コメント本文、返信があれば3行目以降に`→`付きで追加）を
焼き込みます。出力は `marugoto/shorts/MMDD_<id>.mp4`。

**⚠️ 単純な「配信開始時刻＋動画尺」の計算だけでは信頼できません。** `logs/MMDD_pipeline.log` の
開始時刻は分精度な上、実際には配信中のフリーズ/再接続で映像時間と実時間が数分単位でズレることが
実測で確認されています（あるケースでは約8分のズレ）。このため、本スクリプトは映像に元々焼き込まれている
日時オーバーレイ（`YYYY-MM-DD HH:MM:SS`、温湿度と一緒に右下に表示）を `tesseract` でOCRし、
目的の時刻に一致するまでオフセットを反復補正する方式を取っています（誤差1〜2秒まで収束）。
ログの開始時刻はあくまで「だいたいこのへん」の初期値・ファイル選定用にしか使いません。

```bash
pip install pytesseract pillow
sudo apt install tesseract-ocr   # tesseractコマンド本体
```

> OCRの切り抜き座標（`OVERLAY_CROP`）は720x720の映像に合わせた決め打ちです。
> 解像度が変わる場合は再調整してください。

### ③ `python compile_shorts.py MMDD` — スワイプ転換で1本に結合

②で作った個別クリップを、`marugoto/MMDD_clips.json` の並び順のまま `ffmpeg` の `xfade`/`acrossfade`
フィルタでつなぎ、スワイプ風の画面切り替え（デフォルト `slideleft`、0.5秒）を入れて結合します
（個別クリップは`marugoto/shorts/`のテンポラリのままです）。転換の種類は `compile_shorts.py` 内の
`TRANSITION` を変更すれば `wipeleft` / `fade` など `xfade` がサポートする他の効果に変えられます。

出力名は `marugoto/MMDD_short_DAY<n>_<title>.mp4`。アップロード待ちのファイルが複数溜まっても
見分けられるよう、DAY数（`sozai/date_list.txt` 由来）と①が付けたタイトルが入ります。

尺が `MAX_SHORT_DUR`（180秒＝ショートの上限）を超える場合は、クリップの並びを時系列のまま
**2本に自動分割**します（`_part1_` / `_part2_`）。割る位置は前後の尺が均等に近くなるクリップの
境目で、それぞれに専用のオープニングが付き、後半のタイトルには `clips.json` の `title_part2`
（①が必ず用意する2つ目のタイトル）が使われます。

### 既知の制限

- ①はClaude Codeのセッション上で実行する。`daily-shorts` スキルで⓪〜④を一気通貫にできるが、cronのような完全な無人実行ではない
- OCR座標は720x720基準（1080x1080で配信された日は720に縮小してから読む）
- 返信マージは同じクリップの字幕に静的に重ねているだけで、返信が来たタイミングに合わせた表示切り替えはしていない
- 時刻の書かれていない実況コメントは「投稿時刻＋その日のズレ（OCRで実測）−12秒」で位置を推定するので誤差がある

## 📤 YouTubeへの自動アップロード（upload_videos.py）

完成した動画を YouTube Data API v3 で公開し、種類ごとに決まった再生リストへ振り分けます。
タイトル・概要欄・タグは、それまで手動で投稿していた書式をそのまま再現します。

| 種類 | ファイル | 再生リスト（タイトルのキーワードで自動検索） |
|---|---|---|
| まるごと版 | `marugoto/MMDD_output.mp4` | 「動体検知」を含むリスト |
| ショート版 | `marugoto/MMDD_short[_partN]_DAY<n>_<title>.mp4` | 「2年目」を含むリスト |

ショートになるか通常の動画になるかは、長さと画面の形でYouTubeが判定するため、API側では指定しません。

### セットアップ

1. Google Cloud Console で YouTube Data API v3 を有効にしたプロジェクトに、**OAuthクライアントID（デスクトップアプリ）**を作成
2. OAuth同意画面の公開ステータスを「本番環境」にする（「テスト」のままだと7日ごとに認証し直しになる）
3. ダウンロードしたJSONをリポジトリ直下に `uploader_credentials.json` として置く
4. 初回実行時に表示されるURLをブラウザで開いて許可すると、`uploader_token.json` が作られる

`uploader_credentials.json` と `uploader_token.json` は `.gitignore` 済みです。**絶対にコミットしないでください。**

```bash
pip install google-api-python-client google-auth-oauthlib
```

### 実行方法

```bash
python upload_videos.py 0910 --dry-run          # 認証・再生リストの確認と、アップ内容の表示だけ
python upload_videos.py 0910                    # 非公開でアップ（テスト用）
python upload_videos.py 0910 --privacy public   # 公開でアップ（本番）
python upload_videos.py 0910 --only short       # 片方の種類だけ
```

- 概要欄とタグの文面は `sozai/description_short.txt` / `sozai/description_full.txt` / `sozai/upload_tags.txt` を編集すれば変えられます
- シーズンが変わったら `upload_videos.py` の `SEASON` / `PLAYLIST_KEYWORDS` を更新してください（そのままだと「2年目」のリストに入り続けます）
- アップ後は `videos.list` で公開状態を、`playlistItems.list` で再生リストの何番目かを読み直して確認します（`daily-shorts` スキルの手順）。公開で上げれば先頭に並ぶので、末尾のままなら公開になっていません

### 二重投稿の防止

- `marugoto/MMDD_upload.json` にアップ済みの動画IDと再生リストへの追加状況を記録し、再実行時は残りの手順だけ行います
- 同じタイトルの動画がすでに再生リストにあれば（手動で投稿済みの日など）アップしません

### ⚠️ ハマりどころ

- **未監査プロジェクトの非公開ロック**：ドキュメント上は「2020年7月28日以降に作られた未監査のAPIプロジェクトから `videos.insert` した動画は非公開にロックされる」とありますが、2026年9月時点の実測では公開できました。後からロックされる可能性はあるので、本格運用するなら監査の申請を推奨します
- **再生リストの位置指定**：自動並べ替えのリストに `position` を指定すると `manualSortRequired` で拒否されます。スクリプトは先頭指定を試し、拒否されたら位置指定なしで追加します（公開日順の自動並べ替えなら、公開した動画は自動で先頭に来ます）
- **WSLでの初回認証**：URLはWindows側のブラウザで開きます。待ち受けは1回きりなので、待っている間に `curl localhost:<ポート>` などで様子を見ると、その1回を消費して `MismatchingStateError` で失敗します
- **チャットリプレイは翌日まで取れない**：配信当日にショートを作って公開すると、コメントが欠けたまま公開されます。`daily-shorts` スキルは「当日分はダウンロードまで、前日分をショート作成→公開」の1日遅れで回します

### ⚠️ タイムベース(tbn)正規化について

YouTubeからDLした動画は、同じコーデック・同じ解像度でも**タイムベース(tbn)が異なる**ことがあります（例: 1/15360 vs 1/90000）。tbnが不揃いのまま `-c copy` で結合すると、タイムスタンプが破壊されて再生時間が異常な値（56年など）になります。

`fast_bird_pipeline.py` は動体検知処理に入る前に、全動画のtbnを `1/15360` に統一します。この処理は `-c copy` ベースなので再エンコードは発生せず、一瞬で完了します。

```python
def normalize_video(input_path):
    """Normalize video timebase to 1/15360 for consistent -c copy concat."""
    output_path = input_path.replace(".mp4", "_fixed.mp4")
    cmd = [
        "ffmpeg", "-y",
        "-i", input_path,
        "-c", "copy",
        "-video_track_timescale", "15360",
        output_path
    ]
    subprocess.run(cmd, capture_output=True, check=True)
    os.replace(output_path, input_path)
```

### アーキテクチャと設計判断

#### なぜ再エンコードしないのか

旧版（`motion_detector.py`）は各クリップを `libx264` で再エンコードしていましたが、16時間分の動画では処理時間が非常に長くなります。新版では ffmpeg の `-c copy`（ストリームコピー）を使い、デコード/エンコードを完全にスキップしています。

トレードオフとして、切り出しがキーフレーム単位になるため、指定位置より数秒手前から始まるクリップが生成されます（合計で30分程度の増加）。内容的にはイベント直前の「前振り」が少し長くなるだけなので、実用上問題ありません。

#### 並列処理の構成

```
ProcessPoolExecutor (max_workers=4)
├── Process 1: 0610-1.mp4 → OpenCV動体検知 → ffmpeg -c copy で切り出し
├── Process 2: 0610-2.mp4 → OpenCV動体検知 → ffmpeg -c copy で切り出し
└── ...
↓ 全プロセス完了後
結合フェーズ: OP + 全クリップ(ソート済み) + ED → ffmpeg concat → 完成
```

各プロセス内では `cv2.setNumThreads(2)` でOpenCVスレッド数を制限し、CPU競合を防いでいます。

## 🧠 動作の仕組み (アルゴリズム)

本システムは、以下のステップで動作します。両バージョン共通です。

### 1. 前処理

パフォーマンス向上のため、動画から読み込んだ各フレームに対して以下の処理を行います。

1. **フレームサイズ縮小**: 解像度を半分にし、計算量を削減します。
2. **グレースケール変換**: 色情報を削除し、輝度情報のみで処理を高速化します。
3. **ガウシアンブラー**: 微小なノイズを平滑化し、誤検出を抑制します。

### 2. 動き検出（コア技術）

OpenCVの`MOG2 (Mixture of Gaussians)`背景差分法をコア技術として採用しています。

- 過去のフレームから統計的な「背景モデル」をリアルタイムに構築します。
- 現在のフレームと背景モデルを比較し、「ありえない変化」を前景（＝動き）として抽出します。
- 影の検出は無効化 (`detectShadows=False`) し、鳥の影などを動きとして誤検出するのを防ぎます。

### 3. 適応型スレッショルド（賢い感度調整）

1フレームごとに平均輝度を計算し、照明条件に応じて検出感度を動的に調整します。

- **夜間 (輝度 < 15)**: 検出を一時停止。赤外線カメラのノイズ等による誤検出を完全に防ぎます。
- **夕暮れ/夜明け (輝度 15〜50)**: 検出閾値を自動的に引き下げ（感度UP）、薄暗い環境での動きを捉えやすくします。
- **日中 (輝度 > 50)**: 通常の感度で動作します。

### 4. イベント管理と動画生成

- `min_area` を超える動きが検出されると、「イベント」として記録を開始します。
- `pre` と `post` の設定に基づき、イベントの開始時刻と終了時刻を決定します。
- `merge` で指定した秒数以内に次のイベントが発生した場合、それらを一つの長いイベントとして自動的に結合します。
- 最終的に確定したイベント区間を、**FFmpeg**を使って元の動画から切り出します。

## 🛠️ パラメータチューニングガイド

最適な結果を得るための調整のヒントです。

| 目的 | 推奨パラメータ | 説明 |
|---|---|---|
| **小さな動きも逃したくない** | `min_area` を小さくする (例: `200`) | 葉の揺れなども検出する可能性があるので、`threshold`も調整が必要 |

| **クリップを長めにしたい** | `pre` と `post` を大きくする (例: `15`) | 動きの文脈が分かりやすくなる |

## ❓ トラブルシューティング

- **動きが全く検出されない**: `min_area` や `threshold` の値を下げてみてください。`--debug`オプション（旧版）を付けて実行し、コンソールに表示される「面積」や「輝度」の値を確認してください。
- **誤検出が多すぎる**: 木の葉の揺れなどを拾っている可能性があります。`min_area`の値を大きくしてみてください。
- **結合後の動画が再生できない / 映像が乱れる**: OP/ED素材と本編のフォーマット（解像度・FPS・コーデック）が一致していない可能性があります。`ffprobe` で双方を確認し、`ffmpeg` でフォーマットを統一してください。
- **結合後の再生時間が異常（56年、26時間など）**: 入力動画のタイムベース(tbn)が不揃いの可能性があります。`fast_bird_pipeline.py` のtbn正規化処理が正しく動作しているか確認してください。手動で確認する場合は `ffprobe -v quiet -show_entries stream=time_base <動画ファイル>` で各ファイルのtbnを比較できます。
- **`HTTP Error 403: Forbidden` でDLできない**: プレイヤークライアントが返したURLがPO Tokenを要求しています。v6.0は自動で別クライアントに切り替えて再試行するため、通常は放置で解決します。全クライアントで失敗した場合はログに手動DL用URLが出力されるので、YouTube Studioから取得して `input/MMDD/MMDD-1.mp4` に配置し再実行してください。
- **`Requested format is not available` が出る**: v5.x以前はフォーマットを決め打ちしていたため発生していました。v6.0は実在するフォーマットを問い合わせてから指定するため、原理的に発生しません。出る場合はスクリプトが古い可能性があります。
- **DLが異常に遅い（`frag 149/5035` のような表示）**: HLS（断片配信）を掴んでいます。v6.0はDASHを優先しますが、DASHが提供されていない動画では発生します。断片数が多いだけで進行はするため、そのまま待てば完了します。
- **完成した動画が途中までしか映っていない**: 中断されたDLがヘッダだけ完全なファイルを残したケースです。v6.0の完成検証で自動検出・再取得されますが、v5.x以前で作られた成果物が残っている場合は `input/MMDD/` の該当ファイルと `marugoto/MMDD_output.*` を削除してから再実行してください。
- **毎回クライアント診断が走る**: `logs/client_cache.json` が削除されているか、前回成功したクライアントが今回は使えない状態です。異常ではありません。
- **処理が遅すぎる**: `frame_skip` を大きくしてください（旧版では `--parallel` の値を増やすことも可能）。
- **PowerDirectorでエラーが出る**: 旧版で `--min_duration 2.0` を設定し、2秒以上の動画のみ出力するようにしてください。
- **メモリ不足エラー**: 旧版で `--batch_size` を小さく（10-20）、`--parallel` を1-2に減らしてください。

## 🔧 既知の制限・改善ポイント

- **OP/EDのフォーマット手動統一が必要**: 本編とコーデック/解像度/FPSが一致していないと concat が壊れる。自動検出して変換する仕組みがあると便利
- **fast版のパラメータがハードコード**: コマンドライン引数化されていない。現状はスクリプト内の `params` 辞書を直接編集する必要がある
- **日本語フォントパスが固定**: `/usr/share/fonts/opentype/noto/NotoSansCJK-Bold.ttc` を前提としている。環境によってはパス変更が必要
- **テキスト焼き込み内容が固定**: 「～コシアカツバメの一日記録～」がハードコードされている
- **キーフレーム起因の尺増加**: `-c copy` の仕様上、完成動画は再エンコード版より約10%程度長くなる
- **GPU未対応**: 動体検知はCPU（OpenCV MOG2）のみ。CUDAバックエンド対応で高速化の余地あり
- **smart版のチャンネル指定がハードコード**: `CHANNEL_HANDLE` をスクリプト内で直接編集する必要がある

### v6.0 (2026-07) - ダウンロード基盤の全面刷新（メジャーバージョンアップ）

> **⚠️ `smart_bird_pipeline.py` はほぼ全面書き換えです（212行 → 883行、元コードの残存率37%）。**
> 差分を1行ずつ追う意味は薄いため、変更内容はこの履歴を参照してください。他のスクリプトに変更はありません。

**背景**: YouTube側の仕様変更により `403 Forbidden`、`Requested format is not available`、HLS断片化などでDLが頻繁に失敗するようになり、「放置して戻ったら失敗していて作業が進まない」状態が続いていたため、**完遂を最優先**する設計に作り替えました。

- ✅ **フォーマット推測の廃止** — `--dump-single-json` で実在フォーマットを取得し、具体的なID（例 `136+140`）で指定。`Requested format is not available` を根絶
- ✅ **クライアント並列診断** — 5クライアントを `ThreadPoolExecutor` で同時に診断し、使えるものだけを選択
- ✅ **診断結果のキャッシュ** — 成功クライアントを日内で引き継ぎ、さらに `logs/client_cache.json` で次回起動にも引き継ぎ
- ✅ **4段階フォーマットフォールバック** — DASH優先・HLS許容。全段階でH.264を強制し再エンコードを回避
- ✅ **ダウンロード完成検証** — `ffprobe` に加え `ffmpeg -sseof` で末尾を実デコードし、ヘッダが尺を偽装した尻切れファイルを検出
- ✅ **エラーの種別判定** — 恒久エラー（フォーマット不在等）は待たず即次へ、一時エラー（403等）のみ 30/60/120/300秒 待機して再試行
- ✅ **中断・再開対応** — `--continue` により数GBの再取得を回避。既存ファイルは検証のうえスキップ
- ✅ **複数日の一括処理** — 過去7日分の未処理日付をまとめて処理（旧版は1日ずつ）
- ✅ **チャットログ統合** — 全配信枠のコメントを実時刻順にマージして `marugoto/MMDD_output.txt` に出力
- ✅ **ログのファイル出力** — `logs/MMDD_pipeline.log` に詳細を記録。コンソールは進捗のみ
- ✅ **起動時の依存チェック** — `yt-dlp` / `ffmpeg` / `ffprobe` の存在を先に確認
- ❌ **`preflight_check()` を廃止** — 推測ベースの事前確認は、実在フォーマット取得方式に置き換えられ不要に
- ❌ **5分ポーリング待機を廃止** — 配信未終了の日付はスキップして他の日付を処理する方式に変更
